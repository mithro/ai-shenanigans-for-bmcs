# KGPE-D16 I²C mux-fabric control & arbitration — netlist-traced

Complete decode of *who controls* the QU9/QU5/U23 I²C fabric described in
[AST2050-BMC-WIRING.md §10](AST2050-BMC-WIRING.md) — every enable, select and
arbitration net traced to its driver through the extracted `.FZ` netlist
(`tools/extract_fz.py` output; queries run 2026-07-18). This settles the control
questions §10.3 left open, and corrects/extends two details of the §10 map.

## 1. QU9 (SN74CBTLV3125 FET switch) enable — automatic, host-power-derived

- All four `OE#` pins (2/5/12/15) sit on net `I2CMUX_ENABLE#`.
- `I2CMUX_ENABLE#` is driven **only** by inverter `U8` pin 12 (74LVC14A);
  the paired input `U8` pin 13 is net `SYS_PWRGD`.
- Therefore: **`I2CMUX_ENABLE#` = NOT(`SYS_PWRGD`)** — the switch is *closed*
  (segments bridged) exactly while host power is good, and *open* with the host
  off. **The BMC has no direct GPIO control over QU9.**

Switch map (pins traced):

| Switch | A side (pin) | B side (pin) | Bridges |
|---|---|---|---|
| 1 | `I2C2SDA` (3) | `I2C7SDA` (4) | BMC I2C2 ↔ mux common |
| 2 | `I2C2SCL` (6) | `I2C7SCL` (7) | BMC I2C2 ↔ mux common |
| 3 | `I2C8SCL` (11) | `I2C8SCL_SW` (10) | aux-panel seg ↔ TPM/PCIe seg |
| 4 | `I2C8SDA` (14) | `I2C8SDA_SW` (13) | aux-panel seg ↔ TPM/PCIe seg |

## 2. QU5 (74HC4052) — always enabled; select lines arbitrated by U23

- `E#` (pin 6) = net `N51800600` = **`QR143` 4.7 kΩ to GND** → **always
  enabled**; channel choice is purely `S1:S0`.
- Common `1Z/2Z` = `I2C7SCL/SDA`. Channels (traced):
  - `Y0` → `I2C8SCL/SDA` (aux-panel segment, §4)
  - `Y1` → unconnected (empty nets)
  - `Y2` → `I2C10SCL/SDA` → **all 8 DIMM A–D slots** (`DIMM_A1…D2` pins 237/238)
  - `Y3` → `I2C11SCL/SDA` → **all 8 DIMM E–H slots** (`DIMM_E1…H2` pins 237/238)

## 3. U23 (74LVC125) select-line ownership — automatic, no BMC enable pin

Pinout traced: BMC pair `AST_I2CS1`(2)→`I2CS1`(3), `AST_I2CS0`(5)→`I2CS0`(6)
gated by `OE#` pins 1/4 = net `N51800495`; SP5100 pair `SB_I2CS1`(9)→`I2CS1`(8),
`SB_I2CS0`(12)→`I2CS0`(11) gated by `OE#` pins 10/13 = net `N51800497`.

The two `OE#` nets are generated by a two-FET priority chain:

```
BMC_PRESENT# ──►|D27 anode1
                |        cathode ── N51800483 ──[QR164 100k → GND]
SB_BIOS_POST_COMPLT# ──►|D27 anode2      │
                                    gate │
                              QQ9 (2N7002): drain = N51800497 [QR162 4.7k → +3V3]
                                                │
                                           gate │
                              QQ10 (2N7002): drain = N51800495 [QR163 4.7k → +3V3]
```

Truth table (OE# active-low):

| `BMC_PRESENT#` | `SB_BIOS_POST_COMPLT#` | QQ9 gate | SB OE# (`N51800497`) | BMC OE# (`N51800495`) | Select owner |
|---|---|---|---|---|---|
| low (BMC present) | low (POST done) | low | **high (SB off)** | **low (BMC on)** | **BMC** |
| any | high (in POST) | high | low (SB on) | high (BMC off) | SP5100 |
| high (no BMC) | any | high | low (SB on) | high (BMC off) | SP5100 |

**Consequence:** ownership is *hardware-automatic*. During POST the host owns
the DIMM-SPD select lines (BIOS reads SPD); once `SB_BIOS_POST_COMPLT#` asserts
(low) *and* a BMC is present, the select lines belong to the BMC's GPIOF4/F5.
There is **no enable GPIO for the BMC to drive** — the only BMC controls in the
whole fabric are:

- `AST_I2CS0` = **GPIOF4** (ball W4, 4.7 k pull-up `QR114` to +3V3_AUX)
- `AST_I2CS1` = **GPIOF5** (ball W3, 4.7 k pull-up `QR115` to +3V3_AUX)

## 4. Correction/extension to §10: the fourth segment is TPM + PCIe SMBus

§10 describes QU9 switches 3/4 as "I2C8↔I2C8_SW" with the aux panel behind the
mux. The netlist shows the full picture:

- **`I2C8` segment** (QU9 A side): `AUX_PANEL1` pins 4/10 (SCL/SDA) + QU5 `Y0`.
  No AST2050 ball is on this net — the BMC reaches it only *through the fabric*
  (I2C2 → QU9 → I2C7 → QU5 Y0), and only while `SYS_PWRGD` is high.
- **`I2C8_SW` side** connects through 0 Ω `QR160/QR161` to nets
  **`I2C13SDA/SCL`**, which fan out through series resistors to:
  - **`TPM1` header pins 13/14** (via 0 Ω array `RN13`) — the segment's
    upstream/master side,
  - **PCIe slots 1–5 SMBus pins** (`PCIE<n>_I2C13SCL/SDA` via `ER21…ER57`).
- Pull-ups: `QR168/QR169` 4.7 k → +3V3_AUX on the `_SW` side; `QR156/QR157` on
  the `I2C8` side.

So with the host **on** (QU9 closed), aux panel + TPM-header I²C + PCIe-slot
SMBus form one bridged segment the BMC can master via QU5 `Y0` (`S1:S0=00`).
With the host **off**, all of it is unreachable.

## 5. Adjacent facts established by the same trace

- **LU1/LU2 (Intel 82574L) are powered from `+3V3_AUX`** (pins 1/10/32 of each)
  — the host NICs are alive on standby power, so the NC-SI channel (D07) is
  electrically testable with the host powered off.
- **`U25` (HT24LC08 FRU EEPROM) pin 3 (`E2`) is strapped to VCC** (+3V3_AUX
  rail) — for a 24C08-class part this selects the *upper* address block, i.e.
  the device answers at **0x54–0x57**, not the 0x50–0x53 stated in §10.2.
  Silicon `i2cdetect` on I2C5 must settle this; treat 0x54 as the primary
  hypothesis. (Same rail also powers `QU9`, `U8`, Super-I/O `OU1`, BIOS flash
  `FU1`.)
- The QU5 select-line pull-ups mean the idle/unclaimed select state is
  `S1:S0 = 11` → **channel Y3 (DIMM E–H)** whenever no buffer drives the lines.

## 6. Driver / model requirements distilled

1. **QEMU:** the fabric is a board-glue device: QU9 closed iff modeled
   `SYS_PWRGD` high; QU5 4-way routing from GPIOF4/F5 (with pulled-high default
   `11`); U23 ownership function of `BMC_PRESENT#` (present in our machine) and
   `SB_BIOS_POST_COMPLT#` (host-model state). When the BMC doesn't own the
   selects, GPIOF4/F5 must have no routing effect.
2. **Linux:** plain `i2c-mux-gpio` on I2C2 with GPIOF4/F5 — no enable GPIO
   exists. SPD/TSOD reads must expect: host off → no ACK (QU9 open); host in
   POST → select lines owned by SB (reads may hit the *wrong bank* — driver
   must not assume ownership before `SB_BIOS_POST_COMPLT#`).
3. **Silicon procedure:** power host on → wait for POST completion → then SPD
   access is safe and BMC-owned. No bus-fight is possible by design (U23
   hardware mutex), but a mid-POST read can be *misrouted*, not corrupted.

All net/pin facts above come from `kgpe.json` (the extracted netlist); the
query scripts are reproducible via `tools/extract_fz.py` + ad-hoc JSON queries
(see `device-driver-program/LOG.md` 2026-07-18).
