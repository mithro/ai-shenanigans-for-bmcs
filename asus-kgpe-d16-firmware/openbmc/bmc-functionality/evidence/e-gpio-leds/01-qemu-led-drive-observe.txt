Goal: mirror the silicon LED-drive evidence (00-silicon-gpio-map.txt, LS/LU ✅)

WHAT IS PROVEN, AND WHY IT IS RIGOROUS
The 'identify' LED is GPIO(G,0) = gpio-560 (led-id-n), GPIO_ACTIVE_LOW. We drive
it from Linux userspace (echo to /sys/class/leds/identify/brightness) and observe
the underlying GPIO line state in /sys/kernel/debug/gpio. That debugfs value is
the aspeed-gpio driver reading back the QEMU model's data register — so a state
change there proves the QEMU MODEL received the write end-to-end:
  userspace echo -> gpio-leds -> aspeed-gpio driver -> QEMU aspeed_gpio model.
(Reading brightness back would only prove the LED class cached a value; reading
the GPIO line proves the hardware model was actually driven.)

Path: C2 kernel (uImage-kgpe-d16) + BusyBox initramfs, machine kgpe-d16-bmc, via
a new `ledtest` init gate (qemu-firmware/initramfs/init) + run-qemu.py boot.
Build: uv run qemu-firmware/initramfs -> repack (init 0755) -> uInitrd-kgpe-d16.
Run:  run-qemu.py boot --append "console=ttyS4,115200n8 earlyprintk ledtest"
      (all under a systemd-run --scope cgroup).

--- /sys/class/leds ---
bmc-status  cpu1-error  cpu2-error  identify
--- gpio 'out' lines, default (LED off) ---
 gpio-516 (bmc-ctl-lockout-n   )
 gpio-545 (led-bmc-status-n    |bmc-status          ) out hi ACTIVE LOW
 gpio-546 (led-cpu2-err-n      |cpu2-error          ) out hi ACTIVE LOW
 gpio-547 (led-cpu1-err-n      |cpu1-error          ) out hi ACTIVE LOW
 gpio-556 (spd-mux-s1          |mux                 ) out lo
 gpio-557 (spd-mux-s0          |mux                 ) out hi
 gpio-560 (led-id-n            |identify            ) out hi ACTIVE LOW
wrote brightness=1 rc=0
identify ON :  gpio-560 (led-id-n            |identify            ) out lo ACTIVE LOW
wrote brightness=0 rc=0
identify OFF:  gpio-560 (led-id-n            |identify            ) out hi ACTIVE LOW
LED-TEST RESULT: PASS
=== LED-DRIVE-OBSERVE-END ===

DECODE: identify defaults 'out hi' (LED OFF, active-low). brightness=1 drives the
line 'out lo' (LED ON); brightness=0 restores 'out hi' (LED OFF). PASS = the line
flips hi->lo on ON and lo->hi on OFF, i.e. the QEMU model tracked the userspace
LED write exactly.

SILICON COMPARISON (00-silicon-gpio-map.txt) — IDENTICAL behaviour:
  silicon: gpio-560 (led-id-n |identify) out hi -> echo 1 -> out lo (LED ON)
                                                 -> echo 0 -> out hi (LED OFF)
  qemu   : gpio-560 (led-id-n |identify) out hi -> echo 1 -> out lo
                                                 -> echo 0 -> out hi
Same gpio number (560), same consumer label (led-id-n |identify), same ACTIVE_LOW
polarity, same hi<->lo transitions. The QEMU debugfs even reports the same
gpio-line-names (led-bmc-status-n, led-cpu1/2-err-n, spd-mux-s0/s1) as silicon,
confirming the QEMU DTS line-name map matches the board. So the QEMU LED-drive
emulation is faithful to the silicon LED-drive evidence.
