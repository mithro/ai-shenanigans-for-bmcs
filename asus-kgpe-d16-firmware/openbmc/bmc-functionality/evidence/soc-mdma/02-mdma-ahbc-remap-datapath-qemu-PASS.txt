DEVICE-MATRIX rows 45 (MDMA) + 49 (AHBC) — end-to-end data path: PASS
=====================================================================

Proves the FULL MDMA data movement path via the AHBC boot-remap aperture:
  1. AHBC8C[0]=1 (devmem 0x1E60008C 32 1) enables the boot-remap: the modeled
     AHBC (hw/misc/aspeed_ahbc_ast2050.c) toggles the SoC's dram_low_alias so
     SDRAM appears at 0x0.. (the low 256 MB aperture).
  2. The 28-bit MDMA engine (hw/misc/aspeed_mdma_ast2050.c) copies src->dst
     within that low aperture.

Validation trick: STRICT_DEVMEM=y blocks /dev/mem on the kernel's RAM banks
(0x40000000+), but the alias window (0x02xxxxxx) is NOT registered as kernel RAM,
so devmem can read/write it — a device-classified view into the aliased DRAM.
  - write 0xDEADC0DE via alias 0x02002000, read it back -> alias is writable DRAM
  - MDMA copy 0x02002000 -> 0x02004000 (4 bytes)
  - read 0x02004000 -> 0xDEADC0DE (the MDMA-copied pattern)

The machine boots normally to userspace with the AHBC+alias present, because the
alias is DEFAULT-DISABLED at reset (§12.3: AHBC8C[0]=0 = boot from static memory).
Faithful: MDMA uses the raw 28-bit address; the alias is only enabled by an
explicit AHBC8C[0]=1 write (which real firmware issues after relocating to high
DRAM). C2 (our Linux) boots; C4/C-UBOOT oracle re-verification tracked.
