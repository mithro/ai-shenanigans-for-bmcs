D15 modern U-Boot — FIRST silicon boot attempt: FAILED (early data abort). Honest write-up.
    2026-07-20. (The QEMU boot works — this is a real G3-silicon-only blocker.)

GOAL: boot the modern OpenBMC evb-ast2400 U-Boot (out/u-boot.bin, with the #167 i2c fix) on the
REAL AST2050 over JTAG, the same way the Raptor U-Boot boots (boot-silicon-uboot.sh).

METHOD (tmp/boot-modern-uboot-silicon.sh -> Pi): reset halt -> ddr2-init.tcl (DDR2 trained + SCU40[6]
set so U-Boot skips its own DDR2 init) -> boot-modern-uboot.tcl (load modern-uboot.bin @0x40000000,
AHB unlock + DRAM->0x0 remap [0x1E60008C bit0], PC=0, resume). Console captured @115200.
md5(modern-uboot.bin) = a4018d1043c7d06be84f105edb6bf867 (staged + verified).

WHAT HAPPENED:
  * Boot mechanics OK: "DDR2 TRAINED", 0x40000000 read-back = 0xdeadbeef, remap 0x0 -> 0x1, "resumed".
  * The U-Boot image is correctly in place: mdw 0x40000000 = ea0000b8 e59ff014 ... (its ARM reset
    branch + ldr-pc vector table).
  * Console @115200: ZERO bytes from the target (only the seriallog header). Not garbage -> not a
    baud mismatch; the target produced no UART output at all.
  * JTAG post-mortem (halt + reg): current mode = ABORT; pc = 0x00000010 (the ARM DATA-ABORT
    vector); sp = 0x0badc0de (poison / uninitialised).

DIAGNOSIS: the modern U-Boot took a DATA ABORT very early in its low-level init — before it set up a
stack in DRAM (SP still the 0x0badc0de poison) and before console init (no output). So it does NOT
boot on G3 silicon yet, even though it boots fine in QEMU.

CONFIDENCE (being honest, per the project rule):
  * HIGH: it is an early data-abort in the modern U-Boot's own low-level init on the JTAG-boot path
    (PC at the data-abort vector + poison SP + no console are unambiguous). The load recipe itself is
    sound — the Raptor U-Boot reaches its prompt with the EXACT same reset/DDR2/load/remap/PC=0 flow.
  * MODERATE (hypothesis, NOT yet root-caused): the fault is the SDRAM re-init. The evb-ast2400 U-Boot
    does not check SCU40[6] (only the Raptor U-Boot does), so its lowlevel_init re-programs the SDMC
    while the code is running FROM DRAM (remapped to 0x0) -> the access to reprogrammed/again-in-
    training DRAM data-aborts. It could instead be a G4-only register access in lowlevel_init that
    faults on the G3. NOT confirmed to the faulting instruction.
  * Did I do something wrong in the SETUP? Considered: the DRAM->0x0 remap + PC=0 is the Raptor recipe
    and is proven for a G3-compatible U-Boot; SCU40[6] IS set by ddr2-init.tcl. So the setup is the
    same one that boots Raptor. The difference is the modern U-Boot's G4 low-level init, not my flow.

FIX PATH (next step, tracked as a #137 sub-task):
  1. Single-step from 0x0 over JTAG (openocd `step`) to catch the exact faulting instruction / the
     lowlevel_init sub-step, OR read the modern U-Boot arch/arm/mach-aspeed lowlevel_init/platform.S
     to find the SDRAM re-init / G4 register access.
  2. Make the modern U-Boot SKIP its low-level SDRAM init on the JTAG-boot (honor SCU40[6] like the
     Raptor U-Boot, or detect DRAM-already-up), as a uboot-patch. Then re-attempt; success = the
     U-Boot banner appears on the console (baud TBD; retry 1200 if 115200 is silent after it runs).
  3. Only after it reaches the prompt can the #167 SCU04[2] i2c fix be silicon-validated (US column).

STATE LEFT: target halted in Abort mode (harmless — any subsequent boot does reset-halt first). Board
at 4W, JTAG-accessible. Raptor U-Boot bin untouched (modern bin staged to a distinct path).

--- REFINEMENT (deeper JTAG probing, same session) ---
Read the modern U-Boot's lowlevel_init in arch/arm/mach-aspeed/ast2400/platform.S and probed the
halted target further:
  * platform.S DOES have the SCU40[6] skip mechanism ("Check Scratch Register Bit 6", line ~330) —
    the SAME flag the Raptor U-Boot uses. And SCU40 (0x1e6e2040) reads 0x000000c0 at fault time =>
    BIT 6 IS SET (bits 7+6). So ddr2-init.tcl set the skip flag correctly.
  * BUT the abort happens in the EARLY init_dram code (platform.S lines 205-330) that runs
    UNCONDITIONALLY, BEFORE the line-330 bit-6 skip check. That early code writes timer regs
    (0x1e782044, 0x1e782030), SCU (0x1e6e2000/40), USB config (0x1e6e200c, 0x1e6e2090), and an
    AST2300 LPC-recover path — any of which could fault on the G3 if it hits an AST2400/2300-only
    register unmapped on the AST2050 (an external AHB data-abort).
  * HONEST CORRECTION: I do NOT yet have the exact faulting instruction. A JTAG disassembly of the
    region the halted PC/LR pointed at (0x180-0x19c) turned out to be the ABORT-HANDLER save-context
    stub (ldr sp,[pc,#-0x148]; str lr,[sp]; mrs lr,spsr; ...), NOT init_dram — the CPU is LOOPING in
    the abort handler (the handler re-faults, same pattern seen in the M1 Zephyr arm_mmu analysis).
    So PC/LR reads reflect the handler, not the original fault site. Pinning the faulting instruction
    needs catching the FIRST fault (a hardware breakpoint at the 0x10 data-abort vector on a fresh
    boot, then reading LR_abt = faulting_insn+8) or reading the LR the handler pushed to the abort
    stack (SP loaded from 0x40).
FIX PATH (sharpened): (a) catch the first fault to get the exact faulting register access, then
either (b1) move the SCU40[6] skip check to the VERY TOP of lowlevel_init so a JTAG-boot skips ALL of
init_dram including the early timer/USB/LPC writes, or (b2) guard/fix the specific G3-unmapped access.
Confidence: HIGH that it's an early-init_dram unconditional access faulting on G3 (SCU40[6] is set yet
it still aborts before the skip check); the SPECIFIC instruction is still UNCONFIRMED.

--- ROOT CAUSE FOUND + PARTIAL FIX (same session) ---
Caught the first fault with a HW breakpoint at the 0x10 data-abort vector: DFSR=0x1 = ALIGNMENT
FAULT. Read SCTLR (CP15 c1) = 0x5107a => bit 1 (A, alignment-fault-checking) = 1. Grep of the U-Boot
source found the smoking gun: arch/arm/cpu/arm926ejs/start.S:97 `orr r0,r0,#0x00000002 /* set bit 1
(A) Align */` — the modern U-Boot's cpu_init_cp15 DELIBERATELY enables alignment-fault checking, then
its early aspeed code does an UNALIGNED access that data-aborts on REAL silicon (which enforces
alignment) while QEMU (lenient — ignores the A bit) boots either way. That is the complete
"boots in QEMU, faults on silicon" explanation. (The double-fault loop on the poison SP is a
downstream effect: any early fault re-enters the abort handler before exception stacks exist.)

FIX (uboot-patches/0004-arm926-disable-alignment-fault-checking-g3.patch): change start.S:97
`orr`->`bic` (clear the A bit — disable alignment-fault checking, standard on ARM systems that do
unaligned accesses). RESULTS:
  * QEMU: still boots fully to `ast#` (A bit is ignored in QEMU) — no regression.
  * SILICON: the alignment abort is GONE. Post-fix JTAG post-mortem: mode = SUPERVISOR (NOT Abort),
    PC = 0x00038480 (running RELOCATED/init code, ~0x38000 bytes deep — vs the old immediate abort at
    0x10), SCTLR = 0x51078 (A bit now 0). So the U-Boot now EXECUTES far into its init on real
    silicon instead of crashing on the first unaligned access. Big step.

REMAINING (new, separate blocker — honestly open): still NO console output on silicon at 115200 OR
1200 baud (88-90 bytes = capture header only). The CPU is in Supervisor mode at PC=0x38480 (past the
abort).

--- REFINEMENT: it's a HANG before console-init, NOT a baud issue ---
Read the console UART divisor latch at 0x1e784000 over JTAG (set LCR DLAB, read DLL/DLM, restore):
  LCR (0x1e78400c) = 0x00,  DLL (0x1e784000, DLAB) = 0x00,  DLM (0x1e784004) = 0x00.
The UART is COMPLETELY UNCONFIGURED (LCR=0 = reset state, divisor=0). The SAME UART worked for the
Zephyr silicon boots once configured, so this is not a JTAG/decode artifact — the modern U-Boot has
NOT reached console/UART init. Therefore the "no console" is because the U-Boot is HUNG (or blocked) in
early board_init_f BEFORE console_init — the 115200/1200 baud attempts were moot (the UART was never
set up). Confidence: HIGH it's a pre-console hang (UART unconfigured after a 20 s window that is far
more than console-init needs); the EXACT hang site (PC~0x38480) is not yet pinned. Likely a G3-vs-G4
difference in an early board_init_f step that polls a peripheral that never responds (clock/PLL wait,
DRAM sizing, or the MAC-EEPROM I2C read). NEXT (#168): disassemble/single-step around PC=0x38480 (or
set a hw breakpoint at the ns16550 init) to find what it's waiting on. The A-bit fix is COMMITTED
(real, validated: QEMU-clean + silicon-past-abort); this pre-console hang is the next #168 sub-step.

--- FURTHER REFINEMENT (disassembly around the halted PC) ---
Halted PC = 0x00038d78; the code there is string/format processing — `ldrb r3,[r4]; cmp r3,#0; bne`,
and notably `cmp r3, #0x25` (0x25 = '%'), the characteristic format-specifier scan of printf/vsprintf.
So it looks like the U-Boot actually REACHED a print call (NOT hung in a peripheral poll before the
console) — yet the UART at 0x1e784000 is still unconfigured (LCR=0/div=0). That re-points the diagnosis
at serial_init: on the G3 the ns16550 console init did not configure the UART (the divisor from the DT
clock-frequency may compute to 0, or an SCU UART clock/reset the init needs isn't done), so print output
goes into an un-set-up UART and is never transmitted at a readable baud. (Alternatively the CPU is
looping inside the format code on a bad string.) HONESTY: PC=0x38d78 here vs 0x38480 earlier were read
across DIFFERENT boots, so that does NOT by itself prove forward progress; and I did not single-step to
confirm reached-print vs looping. NEXT (#168): hw-breakpoint ns16550 serial_setbrg/init to see why the
LCR/divisor stay 0 on the G3 (compare to the Zephyr UART init, which DOES set the divisor at
0x1e784000), then fix serial_init. Net for the cycle: the alignment abort is FIXED + committed; the
UART-not-configured-on-G3 issue is the precise next sub-step.
