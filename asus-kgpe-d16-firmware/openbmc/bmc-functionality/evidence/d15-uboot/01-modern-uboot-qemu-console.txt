D15 modern U-Boot — boots to its console on the faithful kgpe-d16-bmc (AST2050) QEMU
    (2026-07-20). Baseline for the #137 modern-U-Boot G3 port.

Establishes that the MODERN OpenBMC U-Boot DOES exist and DOES run on the AST2050
QEMU machine (refuting any "no U-Boot drivers exist" claim). This is the C2 boot
stack's bootloader.

Binary: asus-kgpe-d16-firmware/qemu-firmware/uboot/out/u-boot.bin
  = OpenBMC U-Boot v2019.04-aspeed-openbmc (commit dbd95a10), evb-ast2400_defconfig,
    built with arm-linux-gnueabi- (build-uboot.sh). 382693 bytes.
Boot method: placed at offset 0 of a 16 MB flash image (mx25l12805d = the machine's
  fmc_model) and booted via -drive if=mtd (the faithful SPI-flash reset-vector path;
  -kernel does NOT work — U-Boot must run from the flash boot vector). QEMU =
  qemu-firmware/qemu/build/qemu-system-arm (the custom kgpe-d16-bmc machine).

  $ qemu-system-arm -M kgpe-d16-bmc -m 128 -nographic -no-reboot \
        -drive file=flash16m.img,format=raw,if=mtd

WHAT WORKS (modern U-Boot, in QEMU on the G3 machine):
  * Runs from the SPI-flash reset vector; relocates; reaches the interactive `ast#` prompt.
  * SoC auto-ID: "AST1100/AST2050-A2,3/AST2150-A0,1" — U-Boot's SCU silicon-revision path
    correctly recognises this as an AST2050 (G3), NOT a mis-ID as AST2400.
  * DRAM controller brought up (reports 56 MiB usable of the 64 MiB — the ~8 MB delta is the
    aspeed VGA framebuffer carve-out at top of DRAM; to be confirmed for the G3 port).
  * Console on serial@1e784000 (UART5/UART2) — the board's dedicated BMC console UART.
  * SPI flash driver: detects mx25l12805d (page/erase/size correct); reads the U-Boot env.
  * Both Ethernet MACs probed: eth0 @0x1e660000 + eth1 @0x1e680000 (matches schematic §7).

REMAINING #137 WORK (this is the "proper G3 port", now scoped by real evidence):
  1. Board identity: it reports "Model: AST2400 EVB" — it is running the AST2400 EVB board
     config on the register-compatible G3 model. A proper port adds a kgpe-d16-bmc / ast2050
     board + defconfig + device tree (analogous to the Zephyr G3 board), not G4-borrowed.
  2. DRAM sizing: reconcile 56 MiB reported vs 64 MiB physical (VGA reserve) so U-Boot sees the
     faithful size.
  3. Per-device U-Boot drivers to exercise from the prompt (i2c probe of the sensor bus, mac,
     sf) and confirm each works on the G3 model.
  4. SILICON validation: boot this modern U-Boot on the real AST2050 over JTAG (the Raptor
     legacy U-Boot already boots on silicon to boot#; the modern one has been proven in QEMU
     here and needs the on-silicon capture).

NOTE the UQ/US matrix columns track the RAPTOR legacy U-Boot (the faithfulness oracle, boots to
boot# on silicon, drives the boot-path SoC blocks). This modern U-Boot is the separate D15/#137
deliverable. Most non-boot devices are justified Ⓝ for U-Boot (a bootloader has no runtime need
to drive the hwmon/FRU/DIMM-LEDs/PSU).

===== PER-DEVICE DRIVER PROBE (interactive console, non-interactive drive) =====
Drove the `ast#` prompt with commands (tmp/uboot-boot/uboot_probe.py: stop autoboot -> version,
i2c bus, i2c dev/probe, sf probe). Results:
  * `sf probe` -> "SF: Detected mx25l12805d with page size 256 Bytes, erase size 64 KiB, total
    16 MiB". The SPI-flash (SMC) U-Boot driver WORKS in QEMU on the G3 machine -> row 2 (BMC_FW1
    SPI flash) modern-U-Boot driver validated in QEMU. (Boot-critical; also read the env above.)
  * `i2c dev 0|1|4` -> "Failure changing bus number (-19)" (-ENODEV) / "No I2C bus selected";
    `i2c bus` lists nothing. ROOT CAUSE: CONFIG_DM_I2C + CONFIG_SYS_I2C_ASPEED are already =y in
    evb-ast2400_defconfig, but the aspeed SoC dtsi leaves every i2c bus status="disabled" and the
    evb board dts enables none. FIX (uboot-patches/0002-kgpe-d16-enable-i2c-buses.patch): enable
    i2c0/i2c1/i2c3/i2c4 (the engines the kgpe-d16-bmc QEMU machine populates). After rebuild:
      ast# i2c bus
      Bus 0: i2c-bus@40   Bus 1: i2c-bus@80   Bus 3: i2c-bus@100   Bus 4: i2c-bus@140
    => the DM_I2C aspeed driver now BINDS all four buses on the G3 machine (`i2c dev N` works).
  * BUT device reads NAK: `i2c md 0x2f fe 1` (W83795, bus1) and `i2c md 0x54 0 4` (FRU, bus4) both
    return "-121" (-EREMOTEIO / no-ACK); `i2c probe` lists no chips. This is NOT the SCU74 pin-mux
    (bus 1 = engine1 = I2C2 has dedicated pads, needs no pinmux, and still NAKs). The SAME QEMU
    devices are read fine by the Zephyr i2c_aspeed_g3 driver (w83795_smoke / fru_smoke QEMU PASS),
    so the QEMU model is faithful to a correct driver -> the U-Boot aspeed i2c driver (ast_i2c.c,
    written for G4/G5) drives the G3 controller in a way the model (and real HW) reject.
    HYPOTHESIS (MODERATE confidence, NOT yet root-caused): the same class as the Linux #93 fix
    (the G3 needs vendor I2C AC-timing / I2CD04 programming that mainline gets wrong for G3). NEXT
    STEP: diff U-Boot ast_i2c.c bus-init against the working Zephyr i2c_aspeed_g3 / vendor G3 init
    to find the exact register the U-Boot driver mis-programs for G3, then patch it. Tracked as a
    #137 sub-item. HONEST: I have not yet confirmed the AC-timing specifically — only that buses
    bind and all devices NAK, and that a known-correct driver (Zephyr) works on the same model.
  * The console is fully interactively drivable (commands echo + execute), so per-device probes
    are a viable validation method going forward.
