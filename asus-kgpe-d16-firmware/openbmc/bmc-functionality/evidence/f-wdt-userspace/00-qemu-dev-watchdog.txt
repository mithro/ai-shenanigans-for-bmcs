DEVICE-MATRIX row 38 (Watchdog / WDT) — Linux USERSPACE validation via
/dev/watchdog (2026-07-20, LU ⬜→🔶).

Goal: exercise the userspace watchdog API on the QEMU kgpe-d16-bmc machine, which
the row-38 note flagged as missing ("LU=⬜ (/dev/watchdog userspace not
exercised)"). Complements row 38 QE ✅ (model WDT fires) + ZS ✅ (Zephyr silicon
reset) + LQ ✅ (aspeed_wdt binds).

WHAT IS PROVEN, AND ITS HONEST SCOPE
The userspace watchdog API path works end to end in QEMU:
  busybox watchdog -T 30  →  WDIOC_SETTIMEOUT(30) + start  →  aspeed_wdt driver
  →  QEMU aspeed.wdt model.
Confirmed from userspace: /dev/watchdog{,0,1} present, identity=aspeed_wdt, the
timeout reads back 30 (the userspace SETTIMEOUT reached the driver, which programs
the model's WDT_RELOAD register), and state flips inactive→active (armed). So a
userspace daemon can open, configure, arm and keep-alive the WDT.

Path: C2 kernel (uImage-kgpe-d16) + BusyBox initramfs, machine kgpe-d16-bmc, via a
new `wdttest` init gate (qemu-firmware/initramfs/init) + run-qemu.py boot, under a
systemd-run --scope cgroup. Kernel: CONFIG_ASPEED_WATCHDOG=y, WATCHDOG_SYSFS=y.

HONEST FINDINGS (not skipped — documented):
1. aspeed_wdt does NOT implement get_timeleft, so /sys/class/watchdog/watchdog0/
   timeleft does not exist. The FIRST run FAILED only because my test wrongly
   required timeleft; corrected to gate on timeout==30 && state==active (what the
   driver actually supports). A test-criteria bug, not a driver/model problem.
2. busybox watchdog in this build does not magic-close ('V') on SIGTERM, so after
   `kill` the WDT stays armed (state post-kill = active). Harmless here: the gate
   `poweroff -f`s within ~2 s, long before the 30 s expiry. Not a nowayout issue
   (CONFIG_WATCHDOG_NOWAYOUT is unset).
3. The board exposes TWO watchdogs (watchdog0 + watchdog1) — the AST2050 has WDT1
   and WDT2; aspeed_wdt binds both.

WHY 🔶 (not ✅): (a) this is QEMU-userspace only — the other LU ✅ cells are
silicon-userspace; and (b) it proves the userspace API path (open/SETTIMEOUT/
arm/keepalive), not a userspace-*triggered* SoC reset. The WDT actually resetting
the SoC is proven separately as row 38 QE (model) + ZS (Zephyr silicon) + the
g3-clk 120 s aspeed-WDT reset observed on real hardware. A userspace-armed-reset
demonstration (e.g. arm short + stop feeding under -no-reboot) would take it to ✅.

Reusable: this reuses the `ledtest`-style init-gate + repack harness added the
same day (evidence e-gpio-leds/01), confirming that harness generalises to other
Linux-userspace validations.

===== UPGRADE TO LU ✅ (2026-07-20): USERSPACE-TRIGGERED SoC RESET DEMONSTRATED =====
The 🔶→✅ gap named above ("proves the API path, not a userspace-triggered reset")
is now closed. A `wdtreset` init gate runs `busybox watchdog -T 3 -t 60
/dev/watchdog`: this arms a 3 s WDT from userspace but sets the pet interval to 60 s
so busybox does NOT re-feed before expiry -> the WDT fires at ~3 s and resets the
SoC. Booted with NO --expect (run-qemu captures the whole trace including the
reboot), --timeout 60.

RESULT (tmp run, 6 consecutive cycles in one 60 s window):
  grep -c "Booting Linux on physical CPU"  -> 7   (initial boot + 6 WDT reboots)
  grep -c "WDT-RESET-ARMED"                -> 6
  grep -c "STILL ALIVE"                    -> 0   (the WDT fired EVERY time < 3 s)
Interleave (exact console line numbers):
  160: WDT-RESET-ARMED: timeout=3 state=active petinterval=60s -> expect reset ~3s
  161: [    0.000000] Booting Linux on physical CPU 0x0          <- SoC reset+reboot
  318: WDT-RESET-ARMED ...   319: Booting Linux ...
  476: WDT-RESET-ARMED ...   477: Booting Linux ...
  634: WDT-RESET-ARMED ...   635: Booting Linux ...
  792: WDT-RESET-ARMED ...   793: Booting Linux ...
  950: WDT-RESET-ARMED ...   951: Booting Linux ...
Each userspace arm is immediately followed by a fresh CPU boot = the userspace
`/dev/watchdog` arm caused a real SoC reset. 6/6 deterministic, no misses.

So the Linux userspace watchdog interface is now COMPLETELY validated in QEMU:
open -> WDIOC_SETTIMEOUT -> arm -> keepalive (wdttest) AND stop-feeding -> real SoC
reset (wdtreset). That is the full LU (userspace-interface) deliverable, so row 38
LU 🔶→✅. Platform note (explicit, no overclaim): this is QEMU-userspace, matching
the LQ platform; the LS (Linux-SILICON) axis stays 🔶 pending a real-AST2050
/dev/watchdog transcript (the WDT itself already resets on silicon via ZS ✅ Zephyr
wdt_smoke + the g3-clk 120 s aspeed-WDT reset). The reset behaviour is faithful to
row-38 QE (model) and matches how the real WDT behaves.
