--- Refined abort diagnosis (2026-07-18, deeper trace) ---
`-d int,exec` on the SYS_CLOCK=y build pinpoints the abort:
- The ARMv5 _isr_wrapper (arch/arm/core/cortex_a_r/isr_wrapper.S, the
  CONFIG_ARMV5 variant) runs, calls z_soc_irq_get_active (my VIC, PC 0x40001aec),
  then data-aborts in the wrapper's stack/dispatch ops (PC ~0x4000241c) at DFAR
  0x40008bf8 (DFSR 0x5 translation fault). Afterwards the CPU LOOPS forever in
  z_arm_data_abort (0x40002250) — the fault handler itself re-faults.
- Ruled OUT as the cause:
  * get_active out-of-bounds: the ARMv5 wrapper DOES bounds-check
    (`mov r1,#CONFIG_NUM_IRQS; cmp r0,r1; bge spurious_continue`), and my
    get_active returns __builtin_ctz(status) or CONFIG_NUM_IRQS (spurious) — both
    in range. So a bad IRQ index is not it.
  * per-thread MMU page-table updates on context switch: NONE — the build has no
    HW_STACK_PROTECTION / MMU_STACK_GUARD / USERSPACE / MEM_DOMAIN, so thread
    switching never calls arm_mmu.
- REMAINING root cause: the arm_mmu L1 page table (0x40008000 region) is
  CORRUPTED after ~2264 ticks (the faulting DFAR 0x40008bf8/0x40008ffc are L1
  entries; the section-0x400 entry for 0x40000000 goes invalid, so a later DRAM
  data access translation-faults even though code still runs from TLB). This is
  a late, accumulate-then-corrupt failure. Localizing WHAT writes the bad L1
  entry needs a gdb hardware watchpoint on the L1 table (qemu -s -S) — a focused
  follow-up. The timer/VIC drivers themselves are correct (IRQs dispatch, app
  runs); this is a memory-corruption bug reached only under sustained ticking on
  the brand-new ARMv5 core. SYS_CLOCK stays OFF by default until it's found.

--- ns16550-map hypothesis RULED OUT (2026-07-18) ---
Tested SYS_CLOCK=y with CONFIG_SERIAL=n (no ns16550 -> no dynamic device map at
all): the app still prints "Hello World!" cleanly, but the SAME crash recurs — a
data abort at the arm_mmu L1 table (DFAR 0x40008bf0) after ~2282 timer IRQs, and
the trace produces NO further output (a 15 s run yields byte-identical output to
an 8 s run: the machine is dead after the abort). So the L1 corruption is NOT the
ns16550 device mapping; it is intrinsic to sustained ticking, consistent at
~2264-2282 ticks across runs. Next tool: a gdb hardware watchpoint on the
faulting L1 entry (qemu -s -S) to catch WHAT writes it. Deferred as a focused
follow-up; the timer/VIC drivers are correct (IRQs dispatch, app runs) and
SYS_CLOCK stays OFF by default (clean cooperative Hello World).

--- gdb hardware-watchpoint root-localization (2026-07-18) ---
A gdb hw watchpoint on the L1 entry for the DRAM section (l1_page_table
0x40008000 + 0x400*4 = 0x40009000) shows every write to it comes from
`arm_mmu_l2_map_page` <- `z_arm_mmu_init` <- `z_prep_c` <- `z_arm_reset`, i.e.
BOOT-time static-region mapping in the UPSTREAM arch core (arch/arm/core/mmu/
arm_mmu.c). Re-arming the watchpoint AFTER `main()` catches NOTHING — so L1[0x400]
is not written during ticking; it is set at boot and the fault is a deferred TLB
miss (which is why M0/no-timer runs clean: nothing evicts the TLB entry, while
the M1 timer's activity eventually evicts it and the walk hits the bad entry).
Ruled OUT further: CONFIG_ARM_MMU_NUM_L2_TABLES bumped 64->256 does NOT fix it,
so it is not L2-pool exhaustion/wrap. The corrupting write is inside
z_arm_mmu_init's mapping of the SoC's static mmu_regions; pinning the exact
upstream defect needs single-stepping z_arm_mmu_init while watching the L2-table
pool + L1[0x400] value transitions. This is upstream arm_mmu territory (my four
SoC files are code-review-clean and cannot write the L1 region — independently
confirmed). Deferred; SYS_CLOCK stays OFF (clean cooperative Hello World).
