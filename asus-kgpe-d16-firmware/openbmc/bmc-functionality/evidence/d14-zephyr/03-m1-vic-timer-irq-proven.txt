So reset -> ARM926 arch init -> MMU -> C runtime -> kernel init -> main() ALL
work: the kernel reaches and runs the application's main(). (Clean config:
cooperative, static-mapped SoC console; no crash, reaches idle.)

THE FIX that got "Hello World": the sample uses printf() (stdout), but the SoC
console (soc/aspeed/ast2050/console.c) had only installed the printk hook, so the
banner (printk) printed while the app's printf went nowhere. Adding
__stdout_hook_install(ast2050_console_out) routes printf to the same polling
UART backend.

CORRECTION (faithfulness): an earlier version of this note wrongly concluded the
boot "silently hangs before main() -> upstream ARM9 core bug." That was MY
misread — a QEMU `-d exec` trace proved the kernel actually reaches
z_thread_entry -> bg_thread_main -> main() -> idle cleanly; main() ran, only its
printf output was unhooked. Consistent with the project rule: the failure was my
code (a missing stdout hook), never the hardware/upstream.

M1 VIC + system timer — written, IRQs delivered, tickful operation still WIP:
- soc/aspeed/ast2050/vic.c: real single-bank G3 VIC (0x1e6c0000) driver, using
  the Linux irq-aspeed-g3-vic SENSE/DUAL/EVENT constants (timer src 16 =
  edge/single/rising, matching the G3 one-pulse-per-expiry delivery).
- soc/aspeed/ast2050/aspeed_timer.c: tickful Timer1 @ 1 MHz, VIC source 16.
- With CONFIG_SYS_CLOCK_EXISTS=y the timer DELIVERS interrupts through the
  cortex_a_r isr_wrapper and the app still boots + prints "Hello World!" — but
  sustained ticking then trips a data abort at the arm_mmu L1 page table
  (0x40008ffc): the SAME brand-new-ARM9 arm_mmu dynamic-mapping breakage that
  forced the static M0 console, now reached via timer-driven thread-switch page-
  table updates. So SYS_CLOCK_EXISTS is left OFF by default (clean cooperative
  Hello World, no crash); the timer/VIC code is committed and re-armed by
  flipping it to y once the upstream arm_mmu dynamic mapping is fixed (or the
  per-thread MMU stack-guard update is disabled).
