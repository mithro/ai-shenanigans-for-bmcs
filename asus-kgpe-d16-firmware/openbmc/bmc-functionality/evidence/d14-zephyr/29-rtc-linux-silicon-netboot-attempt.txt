THE BLOCKER (specific): `dhcp` in U-Boot gets NO response:
    aspeednic#0: PHY at 0x20
    BOOTP broadcast 1 .. BOOTP broadcast 5
    Retry count exceeded; starting again      <- loops forever
The board's mgmt NIC (ftgmac100, PHY 0x20) TRANSMITS BOOTP broadcasts but RECEIVES
no reply, so it never gets an IP/serverip and the TFTP + bootm never run. Linux is
never booted, so the RTC driver never executes.

CONFIDENCE THIS IS NOT AN RTC BUG: HIGH.
- The RTC code never runs — the failure is entirely in the netboot TRANSPORT
  (U-Boot DHCP), upstream of Linux.
- The identical RTC path (VIC 22 + field-packed RTC04) is ALREADY silicon-proven
  for the Zephyr alarm (evidence /28), and the Linux driver+dtb are QEMU-validated
  on VIC 22 (RTC-LINUX + wakealarm PASS).

LIKELY ROOT CAUSE (for the NETBOOT, not the RTC), two candidates:
1. No DHCP server on the BMC mgmt network right now (the Pi's dnsmasq PXE setup is
   documented for the HOST network; the BMC mgmt port may be on a different / not-
   currently-served segment or uncabled).
2. U-Boot aspeednic RX not working — plausibly the SAME MACCR bit19 FAST_MODE
   speed issue that the Linux ftgmac100 RX fix addressed (10M-on-100M -> rx=0);
   the Raptor U-Boot 2013.07 aspeednic driver may not clear/re-derive it, so BOOTP
   replies are transmitted by the server but not received by the BMC.
