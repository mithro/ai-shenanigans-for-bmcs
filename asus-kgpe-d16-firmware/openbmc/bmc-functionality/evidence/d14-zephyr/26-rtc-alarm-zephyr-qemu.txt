#187 — Zephyr RTC alarm API (RTC04 + VIC-26) on the AST2050 G3 (2026-07-21)
================================================================================
DEVICE-MATRIX row 39 (AST2050 G3 RTC) — Zephyr alarm: implemented + QEMU-validated.
This closes the Zephyr QEMU half (ZQ) of #187, on top of the already-validated
Zephyr set/get driver and the QE alarm model + Linux (LQ/LU) alarm driver.

DRIVER (zephyr/drivers/rtc/rtc_aspeed_g3.c) — added the Zephyr rtc_driver_api
alarm ops to the existing counter-style set/get driver:
  - alarm_get_supported_fields -> SECOND|MINUTE|HOUR (RTC04 has no day/mon/year;
    the counter "day" is a free-running up-counter, not a calendar day — same
    reasoning as get_time, and matching the Linux sibling driver which also
    matches on hour:min:sec only).
  - alarm_set_time: program RTC04 (0x04) byte-packed [23:16]=hour [15:8]=min
    [7:0]=sec from ONLY the enabled fields, then RMW CONTROL (0x0C) to set the
    per-field enable bits [1:3], preserving ENABLE[0] and never writing 1 back to
    the RESTART status bit[5]. mask==0 disables (clears [1:3]).
  - alarm_get_time: unpack RTC04 + rebuild the mask from CONTROL[1:3].
  - alarm_is_pending / alarm_set_callback: per the Zephyr contract.
  - ISR (VIC source 26): the Zephyr contract keeps the alarm ARMED (recurring)
    until disabled, so — UNLIKE the Linux one-shot handler — the ISR does NOT
    clear the CONTROL enable bits; it just delivers the event (callback, else
    latch pending). The framework z_soc_irq_eoi() clears the latched VIC edge.
  - init: IRQ_CONNECT(26)+irq_enable(26); a file-static rtc_g3_isr_dev (set
    before irq_enable) lets the ISR recover the device (mirrors the GPIO driver).
  - concurrency: a per-device k_spinlock guards the CONTROL RMW (shared with the
    ISR) and the callback/pending state; the callback is invoked OUTSIDE the lock.
  VIC source 26 is already edge/falling in the RE'd G3 VIC map
  (soc/aspeed_g3/ast2050/vic.c: SENSE bit26=0, EVENT bit26=0), so no VIC change.

SAMPLE (samples/rtc_smoke): CONFIG_RTC_ALARM=y; a second test half arms
12:00:05, registers a callback, and BUSY-POLLS (not k_msleep — the QEMU RTC
counter advances on a QEMU-internal timer as virtual time passes, so a busy loop
keeps the CPU executing and virtual time advancing until VIC-26 fires; this does
not depend on the guest system tick). Then disarms (mask 0).

===== CODE-REVIEW FINDING + FAITHFULNESS + DETERMINISM FIXES (2026-07-21) =====
An independent review of the new Zephyr alarm driver found ONE real defect
(confidence 92) and validating it flushed out a QEMU-model faithfulness gap:

1. DRIVER (rtc_aspeed_g3.c set_time): the counter-enable CONTROL write was a
   plain, unlocked `write(ENABLE)` that unconditionally cleared CONTROL — so once
   the alarm feature could set CONTROL[1:3], calling rtc_set_time() AFTER arming
   silently DISARMED the alarm (a deterministic contract violation: the Zephyr
   contract keeps an alarm armed until disabled via rtc_alarm_set_time). FIX: made
   it an RMW under the driver's k_spinlock, preserving the alarm-enable bits and
   never writing back the RESTART status bit. Regression-tested (below).

2. QEMU MODEL (hw/misc/aspeed_rtc_ast2050.c, submodule) faithfulness: the
   alarm-check timer compared only the single LIVE counter each tick. The counter
   advances as calendar seconds, so a sec+min+hour alarm matches at exactly ONE
   tick/day; if the timer ran late (a tight guest poll starving the QEMU main
   loop) the live counter had already passed that one matching tick and the exact
   `==` missed — next match a day away. On silicon the comparator is combinational
   and the VIC latches the edge the instant the counter reaches the alarm; it
   cannot be starved. FIX: a bounded rising-edge CATCH-UP SCAN checks every
   counter value crossed since the last check, so no match tick is ever skipped
   (new vmstate field alarm_last_abs, version 4). This was a REAL model bug the
   Zephyr test exposed (the Linux wakealarm had passed by luck).

3. SMOKE (rtc_smoke) determinism: the initial busy-poll used a tight asm spin
   (never yields -> QEMU can't fire the virtual timer) then k_busy_wait (depends
   on the unreliable guest tick/cycle-counter on this ARM926 port) — both flaky.
   FIX: wait by HALTING the CPU (k_cpu_atomic_idle/WFI). When the guest halts,
   QEMU warps virtual time to the next timer deadline, fires the alarm timer, and
   wakes the CPU on VIC-26 — deterministic and tick-independent, exactly how a
   real consumer waits.
