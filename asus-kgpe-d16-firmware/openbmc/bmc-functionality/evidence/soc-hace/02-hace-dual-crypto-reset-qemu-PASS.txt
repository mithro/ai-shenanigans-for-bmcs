DEVICE-MATRIX row 43 (HACE) — QEMU faithfulness: BOTH documented crypto resets gate compute
=============================================================================================

The AST2050/AST1100 A3 datasheet (V1.05) gives the Hash & Crypto Engine TWO
reset inputs, not one:
  * SCU04[4] = AES_RST_N — named as the crypto engine reset in the §8.2 "Clock
    and Reset Tree Mapping Table" ("Crypto Engine  AES_RST_N  PCLK MCLK YCLK").
  * SCU04[5] = hrstn      — the datasheet's Figure 43 "Crypto Engine Reset".
Only SCU04[4] is held at the SCU04 power-on default (0x000FFE5C: bit4=1, bit5=0),
so the silicon SHA-256 validation (evidence 01) only ever exercised bit 4. The
QEMU g3-hace-gate previously gated compute on SCU0C[13] (YCLK) OR SCU04[4] only —
it ignored the second documented crypto reset. Fixed in hw/misc/aspeed_scu.c
aspeed_2050_scu_propagate_gates(): compute is now held when SCU0C[13] OR SCU04[4]
OR SCU04[5] is asserted (opt-in-by-connection; G3-only, other SoCs untouched).

This transcript proves all four transitions in QEMU (the 'hacetest' initramfs
gate). The KEY new lines are 3 and 4 — with YCLK running and AES_RST_N released,
asserting hrstn (SCU04[5]=1) alone holds the engine off, and releasing it lets
SHA-256 complete again — proving the added bit-5 term is functional, not dead code:
  1. YCLK stopped   (SCU0C[13]=1)          -> HASH_IRQ CLEAR (held)      PASS
  2. all released                          -> HASH_IRQ SET   (computed)  PASS
  3. hrstn held     (SCU04[5]=1)           -> HASH_IRQ CLEAR (held)  <-- NEW
  4. hrstn released (SCU04[5]=0)           -> HASH_IRQ SET   (computed) <-- NEW
No KGPE-D16 firmware exercises the crypto engine, so bit 5 could not be silicon-
validated; the model is grounded in the datasheet + proven functional in QEMU.
