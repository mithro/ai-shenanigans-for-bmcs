# KGPE-D16 AST2050 BMC — hardware wiring for power control (F2) & sensors (F3)

Research notes for implementing OpenBMC **F2 (host power control)** and **F3
(sensors)** on the ASUS KGPE-D16's onboard ASPEED **AST2050** BMC. Every claim is
cited. Where the real wiring is only known from a proof-of-concept port (not from
a public schematic), that is called out with a confidence tag and a
confirm-on-hardware method.

> **Headline confidence.** The GPIO power map and the sensor I2C bus below are
> **not guesses** — they come from **Raptor Engineering's actual (PoC-quality)
> OpenBMC port for this exact board**, `raptor-engineering/ast2050-yocto-openbmc`
> (a fork of Facebook OpenBMC), whose board files encode the real
> AST2050-ball → board-signal mapping and the working power/fan sequences. The
> chief remaining uncertainties are (a) the Linux I2C **adapter-index vs. DTS
> alias** for the hwmon bus, (b) the **exact SCU pinmux bit polarity** per pin
> (auto-generated by Raptor's parser; validate against the datasheet), and (c)
> the **PMBus PSU** address. All three are confirmable on the rig (P2A GPIO/SCU
> reads, JTAG AHB, or `i2cdetect` once a BMC image runs).

> **Two of Raptor's files are stale Facebook-Wedge leftovers, not board truth.**
> `lm_sensors/.../asus.conf` (tmp75/fancpld/ast_adc/fb_panther_plus) and the
> generic `power_led.sh`/`post_led.sh` (GPIOE5 power LED, GPIOG/GPIOB POST-LED
> nibbles) describe a Facebook switch, **not** the KGPE-D16. The
> board-authoritative sources are `board_gpio_table_v1.py` +
> `data/asus-BMC-GPIO.csv` + `setup-gpio.sh` (GPIO) and
> `sensor-setup.sh`/`setup-fan.sh`/`init_pwm.sh`/`get_fan_speed.sh` (sensors),
> which are mutually consistent. This doc uses only the authoritative set and
> flags the leftovers inline.

## 1. Host power control (F2)

### 1.1 The authoritative pin map

Raptor's board GPIO CSV maps each AST2050 package ball to a named board signal.
Reproduced verbatim (`meta-raptor/meta-asus/recipes-utils/openbmc-gpio/files/data/asus-BMC-GPIO.csv`):

```
D11,GPIOA4_PHYLINK,Out,ASUS_BMC_CTL_LOCKOUT_N,"Lock out BMC access to board controls.  Active low"
A11,GPIOB1_FLBUSY#,Out,CTL_REQ_POWERUP_N,"Engage mainboard power.  Active low"
D9,GPIOB6_VBDO,Out,CTL_REQ_RESET_N,"Reset mainboard.  Active low"
V4,GPIOF0_VP8,Out,CTL_REQ_POWERDOWN_N,"Forcibly power off mainboard.  Active low"
W4,GPIOF4_VP12,Out,CTL_REQ_SPD_MUX_S1,"SPD mux pin S1"
W3,GPIOF5_VP13,Out,CTL_REQ_SPD_MUX_S0,"SPD mux pin S0"
T4,GPIOE3_VP3,Out,LED_ERR_CPU1_N,"CPU1 error indicator"
R1,GPIOE2_VP2,Out,LED_ERR_CPU2_N,"CPU2 error indicator"
R2,GPIOE1_VP1,Out,LED_STA_BMC_N,"BMC status LED"
Y4,GPIOG0_VP16,Out,LED_STA_LOC_N,"BMC locator LED"
Y3,GPIOG1_VP17,In,USR_SW_LOC_N,"BMC locator switch"
A12,GPIOH2_SDA7,In,STA_LINE_POWER,"Mainboard power status.  1 = power on, 0= power off.  (I2C bus power)"
```

The generated `board_gpio_table_v1.py` and the sysfs init `setup-gpio.sh` agree
exactly with this (every output defaults to `1` = de-asserted for these
active-low lines; `GPIOG1`/`GPIOH2` are inputs). That mutual consistency is why
this map is treated as **high confidence**.

### 1.2 Power semantics — a 3-request-line protocol, NOT raw ATX pins

Key architectural point for F2: the AST2050 **does not** drive raw front-panel
`PWRBTN#`/`RSTBTN#` or the PSU `PSON#`/`PWROK` directly. It drives three
**active-low request lines** into the board's power-sequencing logic (SP5100
southbridge / onboard glue), and reads one **power-state input**:

- `CTL_REQ_POWERUP_N` (GPIOB1) — "engage mainboard power".
- `CTL_REQ_POWERDOWN_N` (GPIOF0) — "forcibly power off".
- `CTL_REQ_RESET_N` (GPIOB6) — "reset mainboard".
- `STA_LINE_POWER` (GPIOH2, input) — 1 = powered on, 0 = off (senses the
  mainboard rail; the pin doubles as the I2C7 `SDA7` ball, repurposed to GPIO).
- `ASUS_BMC_CTL_LOCKOUT_N` (GPIOA4) — a lockout/arbitration line that hands
  control of the request lines to the BMC (asserted low → BMC in control); the
  BMC de-asserts it (=1) at init in `setup-gpio.sh`.

There is **no host power button routed into the BMC** as an input (only the
locator/ID switch `USR_SW_LOC_N` on GPIOG1). The physical ATX power button is
handled by the board's own logic, not the BMC.

The exact sequences the BMC must emit (verbatim from `asus_power.sh`):

```sh
# power ON
gpio_set CTL_REQ_POWERDOWN_N 1
gpio_set CTL_REQ_RESET_N 0
gpio_set CTL_REQ_POWERUP_N 0
sleep 1
gpio_set CTL_REQ_RESET_N 1
gpio_set CTL_REQ_POWERUP_N 1

# power OFF (ungraceful)
gpio_set CTL_REQ_RESET_N 1
gpio_set CTL_REQ_POWERUP_N 1
gpio_set CTL_REQ_POWERDOWN_N 0
sleep 1
gpio_set CTL_REQ_POWERDOWN_N 1

# RESET (warm)
gpio_set CTL_REQ_POWERDOWN_N 1
gpio_set CTL_REQ_RESET_N 0
gpio_set CTL_REQ_POWERUP_N 1
sleep 1
gpio_set CTL_REQ_RESET_N 1

# status
asus_is_us_on() { [ "$(gpio_get STA_LINE_POWER)" == "1" ]; }   # 1 => on
```

(from `asus_power.sh` / `board-utils.sh`, `meta-raptor/meta-asus/recipes-asus/fbutils/files/`.)

### 1.3 LEDs and the ID switch

- `LED_STA_BMC_N` (GPIOE1) — BMC heartbeat/status LED, active low.
- `LED_STA_LOC_N` (GPIOG0) + `USR_SW_LOC_N` (GPIOG1) — the classic
  **identify/locator LED + button** pair (OpenBMC "identify" group). Active low.
- `LED_ERR_CPU1_N` (GPIOE3), `LED_ERR_CPU2_N` (GPIOE2) — per-socket error LEDs
  (dual-Opteron board), active low.

> ⚠️ **Ignore `power_led.sh` and `post_led.sh`.** Those two scripts are unmodified
> Facebook-Wedge generics: `power_led.sh` drives **GPIOE5 (sysfs 37)** and
> `post_led.sh` drives a hex display on **GPIOG0-3 + GPIOB4-7** — pins that either
> aren't in the board table or *conflict* with it (GPIOB6 is the reset line, not
> a POST-LED bit). They are not KGPE-D16 wiring. The board-true LEDs are the five
> in `asus-BMC-GPIO.csv` above.

### 1.4 SCU pin-mux — selecting GPIO mode over the alternate function

All twelve balls are shared-function pins; firmware must select GPIO mode in the
AST2050 SCU **Multi-function Pin Control** registers (datasheet §"Multi-function
Pins", SCU70 strap + SCU74/78 function-select + SCU80/84/88/8C control) before
using them. The per-pin selectors (from Raptor's
`meta-aspeed/.../data/ast2050-gpio.csv`, which the `asus_gpio_parser.py` compiles
into the SCU writes):

| GPIO | Ball | Alt function | SCU selector for the alt fn (clear it for GPIO) |
|---|---|---|---|
| GPIOA4 | D11 | PHYLINK | `SCU74[25]` |
| GPIOB1 | A11 | FLBUSY# (SPI-flash busy) | `SCU74[2]` |
| GPIOB6 | D9 | VBDO / WDTRST | `Strap[5]` (SCU70) + `SCU78[3]`; GPIO also needs `SCU80[14]=0` |
| GPIOE1 | R2 | VP1 (video port) | `SCU74[22]` (whole VP0-7 group) |
| GPIOE2 | R1 | VP2 | `SCU74[22]` |
| GPIOE3 | T4 | VP3 | `SCU74[22]` |
| GPIOF0 | V4 | VP8 | `SCU74[22]` |
| GPIOF4 | W4 | VP12 | `SCU74[23]` (VP12-15 group) |
| GPIOF5 | W3 | VP13 | `SCU74[23]` |
| GPIOG0 | Y4 | VP16 | `SCU84[0]=0` |
| GPIOG1 | Y3 | VP17 | `SCU84[1]=0` |
| GPIOH2 | A12 | SDA7 (I2C7) | `SCU74[14]` |

Concrete SCU-clear examples that Raptor's own scripts spell out (authoritative
for those balls): `post_led.sh` → GPIOB4-7 need `SCU80[12..15]=0` (+ `SCU70[14]`
strap), GPIOG0-3 need `SCU84[0..3]=0`; `power_led.sh` → GPIOE5 needs
`SCU80[21]=0, SCU8C[14]=0, SCU70[22]=0`. Note the GPIOE/F "video-port" balls
belong to a group gate as well — the whole VP0-15 group is gated by
`SCU74[22]`/`SCU74[23]`, and GPIOE additionally has the MII/RMII-vs-VP/TACH group
mux at `SCU74[27]` (datasheet §3.5, p.59; cross-referenced in
`../../qemu-model/peripherals/gpio/DATASHEET-GPIO.md`).

> **Validate polarity on hardware.** The exact set/clear value per pin is
> generated by `asus_gpio_parser.py` from the CSV; the datasheet's Multi-function
> Pin Control chapter is the oracle. Because GPIOB6, GPIOB1, GPIOA4 and GPIOH2
> share pins with the **SPI-flash, PHY and I2C7** functions, a wrong SCU write can
> disturb boot flash or the NIC — read back SCU70/74/78/80/84/8C over P2A or JTAG
> AHB after programming and diff against the datasheet before trusting it.

### 1.5 What is genuinely NOT knowable from public sources

The ASUS KGPE-D16 schematic is not public (Raptor holds it under NDA). Everything
in §1.1–1.4 is derived from Raptor's port, which *is* the schematic knowledge
encoded in software — so it is the best obtainable evidence, but two things are
worth independent confirmation on the rig:

1. That these balls still carry these functions on **your** board revision
   (Raptor's CSV has no explicit board-rev gating for the power pins; the only
   rev pins are `GPIOY0..2 = BOARD_REV_ID*`, which don't exist on the AST2050
   pin map and are themselves Facebook leftovers).
2. The **default/at-reset** level of `STA_LINE_POWER` and the request lines.

**How to confirm on hardware (no BIOS flash, non-destructive):**
- Over **P2A** (culvert) or **JTAG AHB**: read `GPIO00`/`GPIO04`/`GPIO20`/`GPIO24`
  at `0x1E78_0000` while toggling host power from the front panel, and watch
  `STA_LINE_POWER` (GPIOH2, in GPIO20 bit lane H) track on↔off.
- Drive `CTL_REQ_POWERUP_N` (GPIOB1) low→high via a devmem write to `GPIO00`
  (bank B lane, bit 1) *after* setting its direction and SCU mux, and observe the
  board power up — this reproduces `asus_power.sh on` directly on the AHB.
- Continuity-probe balls A11/D9/V4/A12 to the board's power circuit (board OFF)
  to physically confirm.

## 2. Sensors (F3)

### 2.1 One hardware monitor: the W83795G, reachable by the BMC on I2C bus 1

The KGPE-D16 uses a single **Nuvoton/Winbond W83795G** hardware-monitor ASIC for
all fan/temp/voltage. It is **dual-homed**:

- **Host side:** on the SP5100 southbridge **auxiliary** SMBus, address 0x2f —
  coreboot `drivers/i2c/w83795` with `register "smbus_aux" = "1"` and
  `device i2c 0x2f` (coreboot 4.11 `asus/kgpe-d16/devicetree.cb`). This is what
  the running-OS `sensors.txt` in `../../hardware-inventory/` shows
  (`w83795g-i2c-14-2f`, PIIX4 adapter).
- **BMC side:** on **AST2050 I2C bus 1** at 0x2f. Raptor's port instantiates it
  exactly there:
  - `sensor-setup.sh`: `modprobe w83795 force=1,0x2f`
  - `setup-fan.sh`: `modprobe w83795 force_w83795=1,0x2f`
  - `init_pwm.sh` / `get_fan_speed.sh`: `…=/sys/class/i2c-adapter/i2c-1/1-002f`

So the W83795G sits on a bus segment the AST2050 taps as its **I2C channel 1**.
This resolves the open question "can the BMC read sensors independently?" — **yes,
on bus 1**. (`i2c-1` is the Linux adapter index in Raptor's old kernel; for a
modern mainline `aspeed-g4`-based DTS confirm which `&i2cN` alias enumerates as
adapter 1 — see §3.3 caveat.)

### 2.2 W83795G channel map (from coreboot config + host `sensors.txt`)

The coreboot `w83795` block enables (verbatim highlights from
`asus/kgpe-d16/devicetree.cb`):

```
register "fanin_ctl1" = "0xff"   # all 8 fan tach inputs FANIN1..8 enabled
register "fanin_ctl2" = "0x00"
register "temp_ctl1"  = "0x2a"   register "temp_ctl2" = "0x01"
register "temp_dtse"  = "0x03"   # DTS (AMD SB-TSI) temp enable, 2 sources
register "volt_ctl1"  = "0xff"   register "volt_ctl2" = "0xf7"
# fan1..8_duty=100, default_speed=100, fan1..8_nonstop=7  (8 PWM outputs)
# vcore1/vcore2 limits (dual-socket), vsen3..vsen13, vdd(3.3V), vsb(3VSB), vbat
register "smbus_aux"  = "1"      device i2c 0x2f on end
```

Cross-checked against the live host `sensors.txt` (same chip):

| Class | Channels present | Notes |
|---|---|---|
| **Fan tach** | `fan1..fan8` (8) | `fanin_ctl1=0xff`. Only fan1 (~2600 RPM) was spinning; other headers unpopulated. |
| **PWM** | `pwm1..pwm8` (8) | one PWM per fan header. |
| **Temp** | `temp1` (thermal diode = CPU), `temp2`,`temp3` (thermistor), `temp7`,`temp8` (AMD AMDSI / SB-TSI = per-socket die) | `temp_dtse=0x03`. |
| **Voltage** | `in0..in11`, `+3.3V`, `3VSB`, `Vbat`, `in15`, `in16` | = Vcore1/Vcore2 (dual Opteron), vsen3-13 rails, VDD/VSB/VBAT per coreboot. |
| **Chassis** | `intrusion0` | chassis-intrusion alarm bit. |

The W83795G part itself: 21 voltage inputs, 8 temperature (6 thermal + 2 DTS), 14
fan-tach inputs, 8 PWM outputs (mainline `drivers/hwmon/w83795.c` header;
`SENSORS_W83795` + `SENSORS_W83795_FANCTRL`). The KGPE-D16 populates the subset
above.

### 2.3 The AST2050's *own* PWM/tach is not used here

The AST2050 has an internal PWM/Tacho controller (regs at `0x1E78_6000`; PWM1-4 on
GPIOC2-C5, TACH0-15 on GPIOE/GPIOF group-1). On the KGPE-D16 those **GPIOE/GPIOF
balls are repurposed as plain GPIO** (LEDs, power-request, SPD-mux — see §1.1), so
the AST2050 fan block is **not wired to any fan**. F3 fan data must come from the
W83795G over I2C, *not* an aspeed-pwm-tacho hwmon. (This is also why the in-repo
`aspeed-bmc-asus-kgpe-d16.dts` has no pwm-tach node — correct.)

### 2.4 Possible PMBus PSU — flagged, unquantified

`sensor-setup.sh` also does `modprobe pmbus`, and the ASUS manual documents an
**SMBus header that connects to the PSU to read PSU information** (works only with
the ASMB4 installed). So a **PMBus PSU** likely hangs off a BMC I2C bus, but
Raptor's scripts don't bind a specific address/bus for it. **Address + bus
unknown** — confirm with `i2cdetect` on each BMC bus once an image runs, or probe
the SMBus header. Common PMBus PSU addresses are 0x58/0x59/0x5a-0x5b.

### 2.5 Do NOT use `asus.conf` as the KGPE-D16 sensor map

`meta-raptor/meta-asus/recipes-utils/lm_sensors/files/asus.conf` is the unmodified
**Facebook Wedge** lm-sensors profile: `tmp75-i2c-3-4x` inlet/outlet temps,
`fancpld-i2c-8-33`, `fb_panther_plus`, `ast_adc-isa-0000`. None of those chips are
on the KGPE-D16. Ignore it; the real chip is the W83795G (§2.1). (Listed here only
so a future reader doesn't mistake it for board data.)

## 3. How OpenBMC expects this described

Two layers: (A) the **kernel device tree** (gpio-line-names, gpio-keys/leds,
i2c hwmon node), and (B) the **userspace config** (phosphor-gpio +
phosphor-state-manager / x86-power-control for F2; phosphor-hwmon or
dbus-sensors/entity-manager for F3).

### 3.1 Device-tree sketch (add to `aspeed-bmc-asus-kgpe-d16.dts`)

```dts
#include <dt-bindings/gpio/aspeed-gpio.h>
#include <dt-bindings/input/input.h>

&gpio {
	status = "okay";
	/*
	 * gpio-line-names is a POSITIONAL list: entry N names line N, where
	 * line N = bank*8 + pin (A0=0, B0=8, C0=16, ... H0=56). Unused lines get
	 * "". Only the 12 board lines below are meaningful; fill the rest with ""
	 * up to the controller's line count. The meaningful (offset -> name) are:
	 *    4  A4 -> "bmc-ctl-lockout-n"     33 E1 -> "led-bmc-status-n"
	 *    9  B1 -> "power-up-req-n"        34 E2 -> "led-cpu2-err-n"
	 *   14  B6 -> "reset-req-n"           35 E3 -> "led-cpu1-err-n"
	 *   40  F0 -> "power-down-req-n"      48 G0 -> "led-id-n"
	 *   44  F4 -> "spd-mux-s1"            49 G1 -> "sw-id-n"
	 *   45  F5 -> "spd-mux-s0"            58 H2 -> "power-state-in"
	 */
	gpio-line-names =
		"","","","","bmc-ctl-lockout-n","","","",           /* A0..A7 */
		"","power-up-req-n","","","","","reset-req-n","",    /* B0..B7 */
		"","","","","","","","",                            /* C0..C7 */
		"","","","","","","","",                            /* D0..D7 */
		"","led-bmc-status-n","led-cpu2-err-n","led-cpu1-err-n","","","","", /* E0..E7 */
		"power-down-req-n","","","","spd-mux-s1","spd-mux-s0","","",         /* F0..F7 */
		"led-id-n","sw-id-n","","","","","","",             /* G0..G7 */
		"","","power-state-in";                             /* H0..H2 */
};

/ {
	leds {
		compatible = "gpio-leds";
		bmc-status { gpios = <&gpio ASPEED_GPIO(E,1) GPIO_ACTIVE_LOW>; };
		identify   { gpios = <&gpio ASPEED_GPIO(G,0) GPIO_ACTIVE_LOW>;
		             /* linux,default-trigger for phosphor-led */ };
		cpu1-error { gpios = <&gpio ASPEED_GPIO(E,3) GPIO_ACTIVE_LOW>; };
		cpu2-error { gpios = <&gpio ASPEED_GPIO(E,2) GPIO_ACTIVE_LOW>; };
	};

	gpio-keys {
		compatible = "gpio-keys";
		id-button {
			label = "id-button";
			linux,code = <KEY_RESTART>;   /* or a custom code for phosphor */
			gpios = <&gpio ASPEED_GPIO(G,1) GPIO_ACTIVE_LOW>;
		};
	};
};

/* W83795G hardware monitor on BMC I2C bus 1 (see §3.3 caveat on the alias) */
&i2c1 {
	status = "okay";
	/* NB: mainline drivers/hwmon/w83795.c has NO of_match_table (only an
	 * i2c_device_id). A bare 'compatible = "winbond,w83795g"' will NOT bind.
	 * Options: (a) small kernel patch adding of_match { "winbond,w83795g" };
	 * (b) instantiate via i2c board_info / 'echo w83795g 0x2f > .../new_device';
	 * (c) module force= as Raptor did. */
	hwmon@2f {
		compatible = "winbond,w83795g";  /* requires driver of_match patch */
		reg = <0x2f>;
	};
};
```

The pin/direction constants (`ASPEED_GPIO(bank,pin)`) match §1.1; the SCU pinmux
(§1.4) must be applied via the pinctrl node or the board's gpio-setup so these
balls leave their VP/flash/PHY/I2C alternate functions.

### 3.2 Power control — phosphor-state-manager / x86-power-control

The KGPE-D16 uses a **3-request-line protocol**, which does not map 1:1 onto
`x86-power-control`'s single-power-button model (that model does soft-off by
*holding* one PowerOut line). Two realistic paths:

**(a) x86-power-control JSON** (`power-config-host0.json`) — maps the lines it
does fit and needs a custom handler for the dedicated off line:

```jsonc
{
  "gpio_configs": [
    { "Name": "PowerOk",   "LineName": "power-state-in",  "Type": "GPIO",
      "Polarity": "ActiveHigh" },                      /* STA_LINE_POWER / H2 */
    { "Name": "PowerOut",  "LineName": "power-up-req-n",  "Type": "GPIO",
      "Polarity": "ActiveLow" },                       /* CTL_REQ_POWERUP_N / B1 */
    { "Name": "ResetOut",  "LineName": "reset-req-n",     "Type": "GPIO",
      "Polarity": "ActiveLow" }                        /* CTL_REQ_RESET_N / B6 */
    /* CTL_REQ_POWERDOWN_N (F0) has no stock x86-power-control slot -> handle
     * force-off with a custom op or via phosphor-state-manager below. */
  ]
}
```

**(b) phosphor-state-manager + a board power op** wrapping the exact
`asus_power.sh` sequences (§1.2) — cleanest fit for the 3-line handshake. Expose
`power-up-req-n`, `power-down-req-n`, `reset-req-n` via **phosphor-gpio**
(`phosphor-multi-gpio-monitor`/`gpio-presence` for inputs;
`phosphor-gpio-monitor` or direct libgpiod for the output pulses) and drive the
up/down/reset pulses on Chassis/Host state transitions, using `power-state-in`
(H2) as the `CurrentPowerState` feedback.

Recommended mapping to OpenBMC state:
- `xyz.openbmc_project.State.Chassis` On  → pulse `power-up-req-n` low 1 s.
- `…State.Chassis` Off → assert `power-down-req-n` low 1 s.
- `…State.Host` Reboot → pulse `reset-req-n` low 1 s.
- `CurrentPowerState` derived from `power-state-in` (1=On).

### 3.3 Sensors — phosphor-hwmon (realistic) vs. dbus-sensors/entity-manager

The W83795G is an old i2c hwmon part; the pragmatic OpenBMC path is
**phosphor-hwmon** reading `/sys/class/hwmon/*` for the `1-002f` device. A
phosphor-hwmon config (`xyz.openbmc_project.Hwmon...conf`, keyed off the DT
device path) sketch:

```ini
# W83795G @ i2c bus1 0x2f  (label -> D-Bus sensor object)
LABEL_fan1  = FAN1
LABEL_fan2  = FAN2
# ...fan3..fan8...
LABEL_pwm1  = FAN1_PWM
LABEL_temp1 = CPU_TEMP        # thermal diode
LABEL_temp7 = CPU1_DIE        # AMD SB-TSI
LABEL_temp8 = CPU2_DIE
LABEL_in0   = VCORE1
LABEL_in1   = VCORE2
LABEL_in3v3 = P3V3            # driver exposes '+3.3V' as in_* / relabelled
LABEL_in3vsb= P3V3_STBY       # '3VSB'
LABEL_vbat  = VBAT
# NB: the exact inN indices differ between w83795g channels and the sysfs
# 'inN_input' numbering — read the running hwmon (`sensors -u`) and map
# label->inN there. GAIN/OFFSET per rail from W83795 scaling & board dividers.
```

**entity-manager + dbus-sensors** is the modern route, but note **dbus-sensors has
no W83795 backend** (it covers ADC/PSU/TMP/NVMe/etc., not the W83795G). So for
this board either (a) stay on phosphor-hwmon, or (b) add a W83795 hwmon config to
dbus-sensors' `HwmonTempSensor`/`PSUSensor` by exposed hwmon path. An
entity-manager JSON *inventory* entry (for Redfish/inventory, even if sensors are
served by phosphor-hwmon) would look like:

```jsonc
{
  "Name": "KGPE-D16 Baseboard",
  "Exposes": [
    { "Name": "W83795G", "Type": "W83795G_stub",   /* no native EM type today */
      "Bus": 1, "Address": "0x2f" }
  ],
  "Probe": "xyz.openbmc_project.FruDevice({'PRODUCT_PRODUCT_NAME':'KGPE-D16'})",
  "Type": "Board"
}
```

> **Bus-alias caveat.** Raptor's kernel enumerated the W83795G as Linux adapter
> `i2c-1`. On a modern `aspeed-g4.dtsi`-based DTS the alias `&i2c1` is I2C
> controller channel 1, but the *Linux adapter index* depends on which `&i2cN`
> nodes are enabled and their probe order. Confirm the W83795 lands where expected
> with `i2cdetect -l` / `i2cdetect -y <n>` (expect a device at 0x2f) once a BMC
> image boots, and pin it in the DTS accordingly.
